# Plan: RuSToat for iPhone, milestone 1 (log in, read, send)

## Summary
Build a native iPhone app for RuSToat with a SwiftUI interface in Apple's Liquid Glass style, running on the same Rust core as the desktop app. This first milestone gets you from logging in to reading and replying in your servers, DMs and groups on your own phone. Later milestones are listed under [iOS roadmap](#ios-roadmap).

## Approach
GPUI is desktop-only and Liquid Glass belongs to SwiftUI/UIKit (iOS 26+), so the iOS **interface** is new SwiftUI code. The **logic** underneath is shared. Most of the library has no GPUI in it: `api/` (REST and the events websocket), `store.rs` (`ChatStore`, which already builds `ServerEntry`, `ChannelSection`, `ChannelEntry` and `TimelineRow`/`MessageRow` view data), `session.rs`, `accounts.rs`, `notify.rs`, `permissions.rs`, `markdown.rs` and `runtime.rs`. The pieces:

1. **A `desktop` Cargo feature** (on by default) on the existing `stoat-gpui` crate. It holds `gpui-kit`, `livekit`, `keyring` and the modules that need them (`ui`, `voice`, `shortcuts`, `themes`, `assets`, `http`, `window_hide`, plus the gpui colour helpers in `rail.rs`). With `--no-default-features`, the library compiles for `aarch64-apple-ios` and `aarch64-apple-ios-sim`.
2. **A new `stoat-ffi` crate** (`ios/stoat-ffi/`) that depends on `stoat-gpui` without default features and exposes a small API to Swift through **UniFFI** (proc-macros, no UDL). It holds a new `AccountController`, which owns one events connection and one `ChatStore` and turns `ConnectionEvent`s into store updates. Swift is told "something changed" through a callback interface and reads plain-record snapshots. Async FFI methods await the existing `runtime::spawn_io` handles, so no second runtime is needed.
3. **An Xcode project generated by XcodeGen** (`ios/project.yml` → `ios/RuSToat.xcodeproj`, not committed). A script builds the Rust core into `ios/build/StoatCore.xcframework` plus generated Swift bindings. The app targets **iOS 26** and uses the system's Liquid Glass: a `TabView` tab bar, `NavigationStack` toolbars, `.glassEffect()`/`GlassEffectContainer` for floating controls such as the composer, and `.buttonStyle(.glass/.glassProminent)`.

**Rejected alternatives:**
- **Moving the shared code into its own `stoat-core` crate.** It's cleaner in the long run, but every `crate::` path and all ~60 test files (`use stoat_gpui::…`) would change at once. The feature gate gets the same result with almost no churn. Splitting the crate can come later.
- **Moving desktop's event dispatch (`ChatView::on_connection_event` in `src/ui/chat.rs:950–1400`) into shared code now.** It's tangled with view state (panes, loading flags, side panels). The iOS controller dispatches the subset it needs. To keep the two from drifting, the store-only part of that dispatch goes in a GPUI-free function in core (`src/live.rs`) with unit tests. Desktop can adopt it later.
- **Rewriting everything in Swift.** Rejected in discussion: it duplicates the API, store and permissions logic and lets the two apps drift apart.

## Assumptions
1. **iPhone only, iOS 26 minimum, portrait-first.** iOS 26 is the first release with Liquid Glass; you confirmed iPhone only.
2. **Installed from Xcode onto your own phone** with automatic signing under your team (`G55L4BQ44C`, a paid individual team; the "Apple Development: Christopher Hultin (87ATGCDMGT)" identity in your keychain belongs to it, and 87ATGCDMGT is a personal identifier, not the team). No TestFlight.
3. **Bundle ID `com.chrishultin.rustoat.ios`.** It's separate from the Mac app's `com.chrishultin.rustoat`, so the two never share Keychain items or notification registrations.
4. **One account in milestone 1.** Sessions are stored under the same `{API URL}#{user ID}` key as desktop (`accounts::keychain_name`), so adding multiple accounts later needs no migration.
5. **Tokens are stored by Swift through the iOS Keychain**, implementing `session::TokenStore` via a UniFFI callback interface. The trait is synchronous and small (`load`/`save`/`clear`), so this is trivial, and it avoids depending on whether the `keyring` crate's Apple store works on iOS.
6. **TLS on iOS uses bundled webpki roots** for `tokio-tungstenite` (`rustls-tls-webpki-roots` as a target-specific feature) and reqwest's default rustls verifier. `rustls-native-certs` (used on desktop) reads macOS trust settings that don't exist on iOS.
7. **Message text uses SwiftUI's built-in Markdown** (`AttributedString(markdown:options: .inlineOnlyPreservingWhitespace)`) on the Markdown `markdown::prepare` already produces. Bold, italics, code spans and links work. Block quotes, code blocks, math and spoilers show as plain text until a later milestone.
8. **No notifications at all in milestone 1,** not even local ones. The app disconnects when it goes to the background and reconnects when it comes back (as desktop does after a dropped connection: on the next `Ready`, clear the loaded history and reload the open channel).
9. **XcodeGen is installed with Homebrew** (`brew install xcodegen`). It's a build-time tool only, and a reviewable `project.yml` beats a hand-edited `.pbxproj`.
10. **UniFFI is pinned to an exact version** (whatever is current when chunk 2 starts, 0.30 or newer). `uniffi-bindgen` runs as a binary target inside `stoat-ffi`, so bindings always match the library version.

## Open Questions
- **App name on the home screen** (deferrable): "RuSToat" unless you prefer something else. It's only `CFBundleDisplayName` in `project.yml`.
- **Desktop adopting `src/live.rs`** (deferrable, not a blocker): should a later desktop milestone switch `ChatView` to the shared dispatch function, so both apps stay in step automatically?

## Plan

### Chunk 1: Build the library without GPUI, for iOS
**Goal:** `stoat-gpui`'s library compiles for iOS without GPUI, LiveKit or `keyring`, while the desktop app and its tests stay unchanged.
**Files likely touched:** `Cargo.toml` (add a `[workspace]` with `members = [".", "ios/stoat-ffi"]`; a `[features] default = ["desktop"]`, with `desktop = ["dep:gpui-kit", "dep:livekit", "dep:keyring", …]`; target-specific `tokio-tungstenite` TLS features for iOS), `src/lib.rs` (`#[cfg(feature = "desktop")]` on `ui`, `voice`, `shortcuts`, `themes`, `assets`, `http`, `window_hide`, `dock`, `banners`, `login_item`, `sound`), `src/rail.rs` (gate its `gpui_kit::Rgba` colour helpers), `src/session.rs` (gate `KeychainStore`/`keyring` behind `desktop`; `TokenStore` and the rest stay), `src/main.rs` and `build.rs` if they need `required-features`, `rust-toolchain.toml` (add `targets = ["aarch64-apple-ios", "aarch64-apple-ios-sim"]`), `README.md` (one line on the feature).
**Depends on:** None
**Risks:**
- A "GPUI-free" module may pull in a desktop-only one through a chain of `use`s the grep didn't show (`prefs.rs` and `places.rs` are suspects). Fix by gating the offending function, not the whole module, and only if the module is needed on iOS.
- A transitive dependency (`revolt-*` via `async-trait`, `image`, `emojis`) might not build for iOS. It's unlikely, since they're pure Rust, but it's the first thing to check.
- Turning the root into a workspace changes `target/` and `Cargo.lock` handling. `.cargo/config.toml`'s darwin runner must keep applying only to the desktop binary.
**How to verify:**
- `cargo check --lib --no-default-features --target aarch64-apple-ios`
- `cargo check --lib --no-default-features --target aarch64-apple-ios-sim`
- `cargo test && cargo clippy --all-targets -- -D warnings` (desktop, default features; must pass unchanged)
- `cargo clippy --lib --no-default-features -- -D warnings`
**Manual check:** `cargo run` still launches the desktop app and connects.
**Shippable when:** The library checks cleanly for both iOS targets with `--no-default-features`, and the desktop build and full test suite are unchanged.

### Chunk 2: The FFI crate, the XCFramework, and an app that launches
**Goal:** A SwiftUI app shell with a Liquid Glass tab bar runs in the iOS simulator and calls into Rust. This proves the whole Rust → XCFramework → Xcode pipeline before any feature work.
**Files likely touched:** `Cargo.toml` (add `"ios/stoat-ffi"` to `[workspace] members`; chunk 1 created the workspace with only `"."` since the crate didn't exist yet), `ios/stoat-ffi/Cargo.toml` (`crate-type = ["staticlib", "lib"]`, `uniffi` pinned, `[[bin]] uniffi-bindgen`), `ios/stoat-ffi/src/lib.rs` (`uniffi::setup_scaffolding!()`, `core_version()`, a wrapper for `api::instance::normalize_instance` as the first real call), `ios/stoat-ffi/src/bin/uniffi-bindgen.rs`, `scripts/ios/build-core.sh` (builds `--release` for `aarch64-apple-ios` and `aarch64-apple-ios-sim`, generates Swift bindings, runs `xcodebuild -create-xcframework` into `ios/build/StoatCore.xcframework` and copies `StoatCore.swift` into `ios/RuSToat/Generated/`), `ios/project.yml` (iOS 26, iPhone only, bundle ID, team, links the XCFramework, a pre-build script phase that runs `build-core.sh` when Rust sources changed), `ios/RuSToat/RuSToatApp.swift`, `ios/RuSToat/RootView.swift` (`TabView` with Home / Servers / You placeholders), `ios/RuSToatTests/CoreBridgeTests.swift`, `.gitignore` (`ios/build/`, `ios/RuSToat.xcodeproj/`, `ios/RuSToat/Generated/`), `README.md` ("Building for iPhone" section).
**Depends on:** Chunk 1
**Risks:**
- The release-mode iOS static library may be large and slow to link, since `revolt-models` and `regex` come along. Acceptable, but watch the first build time and use `lto = "thin"` in the FFI profile if the app binary passes ~50 MB.
- Xcode's sandboxed script phases can't find `cargo` from `PATH`. The script must source `~/.cargo/env` and set `ENABLE_USER_SCRIPT_SANDBOXING = NO` for that phase.
- UniFFI's Swift output and Swift 6 strict concurrency may disagree (`Sendable` warnings). Set the generated file's target to Swift 5 language mode if needed.
**How to verify:**
- `scripts/ios/build-core.sh && (cd ios && xcodegen generate)`
- `xcodebuild -project ios/RuSToat.xcodeproj -scheme RuSToat -destination 'platform=iOS Simulator,name=<an iPhone from xcrun simctl list devices available>' test`, where `CoreBridgeTests` asserts that `normalizeInstance("stoat.example.com") == "https://stoat.example.com"` and that `coreVersion()` matches `Cargo.toml`.
- `cargo test -p stoat-ffi && cargo clippy -p stoat-ffi --all-targets -- -D warnings`
**Manual check:** Launch in the simulator and see the glass tab bar float over content and shrink as a list scrolls (`.tabBarMinimizeBehavior(.onScrollDown)`).
**Shippable when:** A fresh clone builds and runs the app in the simulator using only the README steps, and the bridge test passes.

### Chunk 3: Log in, 2FA, and staying logged in
**Goal:** Log in to any Stoat instance (with 2FA if your account uses it), keep the session in the iOS Keychain, and come back already signed in on the next launch, or with "Retry" if Stoat can't be reached.
**Files likely touched:**
- `ios/stoat-ffi/src/session.rs`:
  - `#[uniffi::export(callback_interface)] trait TokenVault { load/save/clear }`, bridged to `session::TokenStore`
  - async `resolve_instance`, `login(email, password)` returning `LoginOutcome { LoggedIn{…} | NeedsMfa{ticket, methods} | Disabled }`, `login_mfa(ticket, code|recovery_code)`, `restore(key)` mapping `session::Restored`, and `log_out`
  - `ApiError` mapped to a flat FFI error enum with the user-facing text from `profile_edit::error_text` or its equivalent
- `ios/stoat-ffi/src/accounts.rs`: the account file at a path Swift passes in (the app container's Application Support). `places::support_dir()` relies on `$HOME`, which iOS sets to the container, but passing the path explicitly is clearer.
- `ios/RuSToat/Session/KeychainVault.swift`: `SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete`, `kSecAttrAccessibleAfterFirstUnlock`.
- `ios/RuSToat/Login/LoginView.swift`: server field (default `https://api.stoat.chat`), email, password, a 2FA step that switches between authenticator code and recovery code; a glass card on a gradient background; `.buttonStyle(.glassProminent)`.
- `ios/RuSToat/AppModel.swift`: an `@Observable` app state with `restoring / offline(retry) / signedOut / signedIn`.
- `ios/stoat-ffi/tests/login.rs`
**Depends on:** Chunk 2
**Risks:**
- UniFFI callback interfaces are called from Tokio threads. `KeychainVault` must be thread-safe; Keychain Services is.
- The flow in `src/ui/login.rs` (lines ~160–200) mixes view state with the calls. Copy only the call sequence, not the view logic.
- Sessions are named "RuSToat" on desktop. Name the iOS one "RuSToat (iPhone)" so it's recognisable in Stoat's Settings → Sessions.
**How to verify:**
- `cargo test -p stoat-ffi --test login`: a wiremock Stoat API covering a plain login, a login needing MFA then succeeding, a wrong password giving the right error text, a restore with a token the server rejects clearing the vault, and a restore while offline keeping it.
- `xcodebuild … test`: a `KeychainVaultTests` round-trip (save → load → clear → load is nil) under a test-only service name.
**Manual check:** In the simulator, log in to your real account (with 2FA if enabled), quit the app, relaunch, and land signed in without seeing the login screen. Log out and confirm the session disappears from Stoat's Settings → Sessions.
**Shippable when:** Login, 2FA, restore and log-out all work against the real instance, and the wiremock tests pass.

### Chunk 4: Connect, and browse servers, channels and DMs
**Goal:** Once signed in, the app connects to the events service and lists your DMs and groups (Home tab) and your servers with their categorised channels (Servers tab), with unread dots and mention badges, updating live.
**Files likely touched:**
- `src/live.rs` (new, in core, GPUI-free): `pub fn apply_event(store: &mut ChatStore, event: ServerEvent) -> Changed` for the store-only effects of `Ready`, `Message`, `MessageUpdate`/`Append`/`Delete`, channel and server create/update/delete, `UserUpdate` and `ChannelAck`, following what `ChatView::on_connection_event` does to the store (`src/ui/chat.rs:950+`). `Changed` says what to re-read (servers, channel lists, or one channel's timeline).
- `tests/live_dispatch.rs`
- `ios/stoat-ffi/src/controller.rs`: an `AccountController` (`#[derive(uniffi::Object)]`) holding `Mutex<ChatStore>`, the `events::Connection`, and a Tokio task draining the receiver into `live::apply_event`. It reports to a `#[uniffi::export(callback_interface)] trait ControllerListener { fn changed(&self, change: Change); fn status(&self, status: ConnectionStatus); }`. Snapshot methods return FFI records mirroring `ServerEntry`, `ChannelSection`, `ChannelEntry` and `home_channels()`, with media URLs resolved via `MediaUrls`.
- `ios/RuSToat/Model/AccountModel.swift`: `@Observable`, re-reading snapshots on `changed`, hopping to `@MainActor`.
- `ios/RuSToat/Home/HomeView.swift`, `ios/RuSToat/Servers/ServerListView.swift`, `ServerChannelsView.swift` (a `List` with category sections), `ios/RuSToat/Shared/AvatarView.swift` (`AsyncImage` with an initial-letter fallback), `ios/RuSToat/Shared/ConnectionBanner.swift` (a glass capsule saying "Connecting…" or "Reconnecting (attempt n)").
- `ios/RuSToat/RuSToatApp.swift`: on `scenePhase` `.background` disconnect, on `.active` reconnect.
**Depends on:** Chunk 3
**Risks:**
- **Drift from desktop.** `live::apply_event` copies the store-related half of desktop's dispatch. If desktop's dispatch changes later, iOS won't follow automatically. Mitigation: put tests in `tests/live_dispatch.rs` that reuse the fixtures under `tests/fixtures/`, and a doc comment on both sides pointing at the other.
- **Snapshot cost.** Re-reading full lists on every event is O(channels). That's fine at personal scale, but coalesce `changed` calls (one per ~50 ms burst) so a `Ready` doesn't cause hundreds of SwiftUI updates.
- **Holding the mutex across `.await`** would deadlock. The controller must lock, apply, unlock, then notify.
**How to verify:**
- `cargo test --test live_dispatch` (Ready fills servers and channels; a Message in an unviewed channel marks it unread; a mention increments `mentions`; ChannelDelete removes it; ServerUpdate renames it)
- `cargo test -p stoat-ffi`: the controller against a wiremock API plus a local websocket that sends a canned Ready, checking that the listener receives `status(Connected)` and `changed(Servers)` and that `servers()` returns the fixture's servers.
**Manual check:**
- On the simulator, check that every server and DM you have on desktop appears, with icons.
- Send yourself a DM from desktop and see the unread dot appear on iOS live.
- Background the app for a minute, return, and see the banner reconnect.
**Shippable when:** You can browse every server, channel and DM signed in on the phone, with live unread state.

### Chunk 5: Reading a channel
**Goal:** Opening a channel or DM shows its messages, newest at the bottom, with avatars, names, times, replies' previews and edited markers. Older messages load as you scroll up, live changes appear in place, and viewing marks the channel read.
**Files likely touched:**
- `ios/stoat-ffi/src/controller.rs`:
  - `open_channel(id)`: `fetch_messages` → `set_history`, as desktop's `ensure_current_loaded`
  - `load_older(id)`: `fetch_messages` before the oldest message → `prepend_page`
  - `timeline(id) -> Vec<TimelineItem>`: from `ChatStore::timeline` + `with_unread_divider`
  - `mark_read(id)`: `ack_message` + `apply_ack`, only while the app is active and the channel is on screen
  - `close_channel(id)`
- `ios/RuSToat/Chat/ChatView.swift`: a `ScrollView` + `LazyVStack` with `.defaultScrollAnchor(.bottom)` and `scrollPosition`. A top sentinel triggers `load_older`. A "New messages" divider. Rows show a header for non-`continuation` messages, and system messages are centred and muted.
- `ios/RuSToat/Chat/MessageRowView.swift`, `ios/RuSToat/Chat/MessageText.swift` (`AttributedString(markdown:)`, with `stoat:user/…` links handled by `OpenURLAction` as a no-op for now), `ios/RuSToat/Chat/ReplyPreviewView.swift`.
- Attachment and embed rows show as a compact placeholder (file name and size, or a thumbnail via `AsyncImage` for images) that opens the URL in Safari. Full media is a later milestone.
**Depends on:** Chunk 4
**Risks:**
- **Scroll position on prepend.** SwiftUI jumps when older rows are inserted above. Keep the row identity stable (`MessageRow.key`) and use `scrollPosition(id:)` to pin the previously-top row. This is the trickiest UI piece in the milestone, so prototype it early.
- **Markdown fidelity.** `markdown::prepare` writes Markdown meant for gpui-component's TextView, including custom link schemes and math blocks. Some of it will look raw in `AttributedString`. Accept that for milestone 1 and list the gaps in the PR.
- **Reconnect.** On a reconnect `Ready`, `clear_histories` must also reload the open channel, or the screen goes blank.
**How to verify:**
- `cargo test -p stoat-ffi`: `open_channel` loads a fixture page; `load_older` prepends and marks the history `exhausted` when the server returns fewer than requested; a live `MessageUpdate` changes the row's `render_key`; `mark_read` posts an ack only when told the channel is visible.
- `xcodebuild … test`: a `MessageText` unit test for bold, italics, code and links.
**Manual check:**
- Open a busy channel and scroll back several pages: no jumps or duplicates.
- Edit and delete a message from desktop and watch it change on the phone.
- Confirm the channel's unread dot clears on desktop after reading it on the phone.
**Shippable when:** You can read any channel's full history on the phone, and reading there marks it read everywhere.

### Chunk 6: Sending messages
**Goal:** A floating Liquid Glass composer sends messages, which show straight away as pending, then as sent, or as failed with a tap-to-retry, and you can reply to a message.
**Files likely touched:**
- `ios/stoat-ffi/src/controller.rs`:
  - `send(channel, text, reply_to: Option<String>)` using `ChatStore::add_pending` → `send_message` with the idempotency key → `fail_pending` on error
  - `retry(channel, key)`, `discard(channel, key)`
  - `typing(channel)`, sending `begin_typing` at most every few seconds, as desktop's composer does
  - `can_send(channel)` from `permissions`
- `ios/RuSToat/Chat/Composer.swift`: a `TextField(axis: .vertical)` in a `GlassEffectContainer` pinned with `.safeAreaBar(edge: .bottom)`, a glass send button, and a reply chip above the field. Swipe right on a row (or long-press → Reply) to reply.
- `ios/RuSToat/Chat/MessageRowView.swift`: pending rows dimmed, failed rows with a red retry badge.
- Drafts per channel, kept in memory (`draft.rs` has the logic if persistence is wanted later).
**Depends on:** Chunk 5
**Risks:**
- **Duplicate rows.** The pending row and the confirming live `Message` must merge via the idempotency key (`MessageRow.key`). If the FFI timeline loses the key, the same message appears twice.
- **Keyboard handling.** The composer must ride the keyboard, and the list must stay pinned to the bottom when the keyboard opens. `.safeAreaBar` handles this on iOS 26, but check it on a real device.
**How to verify:**
- `cargo test -p stoat-ffi`: a send shows a pending row immediately; a successful POST and the live echo leave exactly one row with no `pending`; a 500 leaves the row `Failed`; `retry` re-POSTs with the same idempotency key; `can_send` is false in a channel without `SendMessage`.
**Manual check:**
- Send messages and replies from the phone and see them on desktop.
- Turn on Airplane mode, send, see the row fail, turn Airplane mode off, tap retry, and see it send once.
**Shippable when:** You can hold a conversation from the phone, and failures are visible and recoverable.

## Test Plan

**Full-suite command:**
```bash
cargo test && cargo clippy --all-targets -- -D warnings \
  && cargo clippy --lib --no-default-features -- -D warnings \
  && cargo check --lib --no-default-features --target aarch64-apple-ios \
  && cargo test -p stoat-ffi \
  && scripts/ios/build-core.sh && (cd ios && xcodegen generate) \
  && xcodebuild -project ios/RuSToat.xcodeproj -scheme RuSToat \
       -destination 'platform=iOS Simulator,name=<available iPhone>' test
```
The first line is the existing desktop suite (README "Tests"). The rest is added by chunks 1–2. Until chunk 2 lands, stop after the `cargo check … aarch64-apple-ios` line. Consider wrapping it all in `scripts/ios/test.sh` in chunk 2.

### Unit Tests
- `live::apply_event` (`tests/live_dispatch.rs`): each event kind's effect on servers, channel lists, unread and mention counts, and timelines, using the existing `tests/fixtures/`.
- `stoat-ffi` record conversions: `MessageRow` → `TimelineItem` keeps `key`, `continuation`, `pending` and reply previews; `ChannelEntry` keeps `unread`/`mentions`/`muted`.
- The FFI error mapping: each `ApiError` kind gives the same user-facing text as desktop.
- Swift: `KeychainVault` round-trip; `MessageText` Markdown rendering; `normalizeInstance` through the bridge.

### Integration Tests
- `stoat-ffi` against wiremock plus a local websocket:
  - login → MFA → connected → Ready → servers listed
  - open channel → load older until exhausted
  - send → pending → live echo merges
  - send fails → retry succeeds
  - token rejected on restore → signed out with the vault cleared
  - offline restore → token kept
  - socket dropped → reconnect → Ready → history reloaded

### Manual Tests
1. Fresh install in the simulator: log in to `api.stoat.chat` with 2FA.
2. Relaunch: already signed in.
3. Browse every server and DM, and compare with desktop.
4. Read a long channel back several pages: no jumps.
5. Send, reply, and fail-then-retry under Airplane mode.
6. Read on the phone, and see the unread state clear on desktop.
7. Background for 5+ minutes and return: it reconnects and the open channel reloads.
8. Light and dark mode: glass elements stay legible over busy content.
9. Log out: the session is gone from Stoat's Settings → Sessions.
10. Install on your physical iPhone and repeat steps 3–7 on cellular.

## Definition of Done
- [ ] `cargo test && cargo clippy --all-targets -- -D warnings` passes with default features, and the desktop app behaves as before.
- [ ] `cargo check --lib --no-default-features --target aarch64-apple-ios` succeeds, and `gpui-kit`/`livekit`/`keyring` don't appear in `cargo tree --no-default-features --target aarch64-apple-ios -p stoat-gpui`.
- [ ] `scripts/ios/build-core.sh` produces `ios/build/StoatCore.xcframework` with device and simulator slices, and `xcodebuild … test` passes on a simulator.
- [ ] Logging in with email, password and TOTP works against `api.stoat.chat`; the token is in the iOS Keychain under `{API URL}#{user ID}` and nowhere on disk.
- [ ] Relaunching restores the session. A token Stoat rejects returns to the login screen; an unreachable server shows Retry.
- [ ] Home lists DMs and groups, and Servers lists every server with categorised channels, unread dots and mention counts that update live.
- [ ] A channel shows its history, loads older pages to the start, applies live edits and deletes, and acks while on screen.
- [ ] Sent messages show as pending, then sent, or as failed with retry, and never appear twice.
- [ ] The tab bar, navigation toolbars, composer and connection banner use system Liquid Glass (`TabView`, `.glassEffect`, `.buttonStyle(.glass…)`), with no custom blur imitations.
- [ ] The app installs and runs on your iPhone from Xcode.
- [ ] README documents building for the simulator and installing on a device.
